// 1. — HARDWARE TOPOLOGY

The Two Wires 🔌

// THE NUMBER THAT EXPLAINS EVERYTHING

NVLink: 900 GB/s. InfiniBand: 50 GB/s. That 18× gap is why every deployment decision changes at the node boundary. It's not a preference — it's physics.

⚡ NVLink + NVSwitch INTRA-NODE

Within one server: GPUs connected via NVLink at 900 GB/s. NVSwitch creates a full mesh — any GPU to any GPU at full bandwidth, no intermediate hops. Critical for all-reduce operations.

🏙️ EMPIRE ANALOGY

The internal dumbwaiter system inside one restaurant building. Dishes travel between floors instantly. Chef on floor 1 can send anything to chef on floor 8 without stepping outside.

🐢 PCIe + InfiniBand INTER-NODE

PCIe (~128 GB/s) connects CPU to GPUs within a node. InfiniBand (~50 GB/s, 2–5µs latency) connects nodes. 18× slower than NVLink, 20–50× more latency. Used for KV cache offload and cross-node parallelism.

🏙️ EMPIRE ANALOGY

Delivery trucks between restaurant locations across the city. Food gets there, but it takes minutes not seconds. You design menus around what's worth trucking vs making locally.

// CEREBRAS — THE EXCEPTION

Cerebras WSE-3: one wafer-scale chip, 850K cores, 44GB on-chip SRAM, no HBM, no inter-chip communication. The "wire between GPUs" problem literally doesn't exist. All of this becomes irrelevant — but you're constrained to what fits on one wafer. The ultimate single kitchen, impossibly large.

// 2. — DATA PARALLELISM

Data Parallelism 🍽️

🔄 Copy the Whole Kitchen SIMPLEST
⚔️ Kills: Throughput limits from single model replica

The entire model lives on every GPU. Different requests go to different GPUs. Zero communication during inference — each GPU runs completely independently. Pure horizontal throughput scaling.

GPU 0: Full model → handles requests 1, 5, 9... GPU 1: Full model → handles requests 2, 6, 10... GPU 2: Full model → handles requests 3, 7, 11... GPU 3: Full model → handles requests 4, 8, 12... Communication during inference: ZERO ✅ Constraint: entire model must fit on ONE GPU
🏙️ EMPIRE ANALOGY

Open identical restaurant locations across the city. Same menu, same recipes, same staff training. Each location serves its own customers independently. No coordination needed — just build more locations when demand grows.

// 3. — TENSOR PARALLELISM

Tensor Parallelism ✂️

➗ Split the Weight Matrix INTRA-NODE ONLY
⚔️ Kills: Single-GPU memory limit for large weight matrices

Individual weight matrices are split across GPUs. Each GPU holds a shard of every layer. After each matmul, results must be combined via all-reduce. Two all-reduces per layer = very high communication frequency.

// Column-parallel (W_Q, W_K, W_V, W_gate, W_up) GPU 0: x @ W[:, :d/2] → partial columns GPU 1: x @ W[:, d/2:] → partial columns → all-gather to concat ✅ // Row-parallel (W_O, W_down) — pairs with column-parallel GPU 0: x[:, :d/2] @ W[:d/2, :] → partial sums GPU 1: x[:, d/2:] @ W[d/2:, :] → partial sums → all-reduce to sum ✅ Trick: column then row = only ONE all-reduce for the pair! // Attention heads align NATURALLY with TP GPU 0 owns heads 0..H/2 → full attention, own KV cache GPU 1 owns heads H/2..H → full attention, own KV cache KV cache shards for free — no extra coordination!
🏙️ EMPIRE ANALOGY

Two sous chefs split the recipe book in half — chef A handles all savory components, chef B handles all finishing sauces. They work simultaneously, then combine at plating. Fast — but they must pass plates to each other every single course. They must work in the same kitchen (NVLink) or the passing takes too long.

Communication cost: 2 all-reduces × 80 layers = 160 all-reduces per forward pass At D=8192, B=32: ~2.7 GB of comms per forward pass → MUST have NVLink (900 GB/s) → InfiniBand (50 GB/s) would add 320–800µs per token ❌

Hidden bonus: More GPUs = weights spread thinner = more HBM per GPU free for KV cache. A 70B model on 8 GPUs leaves ~62 GB per GPU for KV cache vs ~20 GB on 2 GPUs. TP isn't just about fitting the model — it's about freeing serving memory.

// 4. — PIPELINE PARALLELISM

Pipeline Parallelism 🏭

🔗 Split the Layers CROSS-NODE OK
⚔️ Kills: Model depth too large for one node

Assign whole layer groups to each GPU. Activations flow forward stage-by-stage like an assembly line. Communication is point-to-point between adjacent stages only — no all-reduce, infrequent, small volume. Works across slow inter-node links.

GPU 0 (Stage 1): layers 1–20 → sends activations [B, D] to GPU 1 GPU 1 (Stage 2): layers 21–40 → sends activations [B, D] to GPU 2 GPU 2 (Stage 3): layers 41–60 → sends activations [B, D] to GPU 3 GPU 3 (Stage 4): layers 61–80 → output ✅ Communication volume: D × B bytes per boundary = 8192 × 32 × 2 bytes = ~0.5 MB (trivial on any link) vs TP's ~34 MB per layer — 68× less per event, far less frequent
🏙️ EMPIRE ANALOGY

Assembly line across restaurant locations: Location A does prep, hands ingredients to Location B for cooking, which hands to Location C for plating, then D for service. Each location specializes in its stage. A dish travels the whole chain — but each location only hands one box to the next, not a constant stream of plates back and forth.

💭 The Pipeline Bubble THE PROBLEM

With P stages and one request, only one stage is active at a time. Bubble fraction = (P-1)/P. At P=4: 75% of hardware idle at any given moment.

ONE REQUEST, 4 stages: Stage 1: ████░░░░░░░░ (works then waits) Stage 2: ░░░░████░░░░ (waits, works, waits) Stage 3: ░░░░░░░░████ (long wait, brief work) Stage 4: ░░░░░░░░░░██ (longest wait) MANY REQUESTS (continuous batching fills the pipeline): Stage 1: ████████████ always busy Stage 2: ░███████████ fills quickly Stage 3: ░░██████████ fills quickly Stage 4: ░░░█████████ fills quickly Inference escapes the bubble because: 1. Decode = 1 token/step → short pipeline latency per step 2. Continuous batching keeps many requests in flight always
🏙️ EMPIRE ANALOGY

One customer through the assembly line = 3 locations idle while the 4th serves them. But a Saturday dinner rush? All 4 locations run at full capacity simultaneously, each handling a different customer's order at a different stage. The bubble disappears when the pipeline stays full.

// 5. — EXPERT PARALLELISM

Expert Parallelism 🧑‍🍳

// THE MOE BARGAIN

MoE models decouple parameters from compute. 256 experts exist, 8 activate per token. Total parameters: huge. Active compute: small. Memory cost: huge — which is exactly what EP distributes.

🗺️ Route Tokens to Expert GPUs ALL-TO-ALL
⚔️ Kills: Can't fit 256 experts on one GPU

Experts are sharded across GPUs. A router decides which 8 experts each token needs. Tokens travel to the GPUs holding their assigned experts, compute, then results return. Communication pattern is all-to-all — unpredictable and irregular.

256 experts, 4 GPUs: GPU 0: experts 0–63 GPU 1: experts 64–127 GPU 2: experts 128–191 GPU 3: experts 192–255 Token A needs experts {7, 45, 89, 134, 156, 201, 223, 251} → must visit GPU 0, GPU 0, GPU 1, GPU 2, GPU 2, GPU 3, GPU 3, GPU 3 All-to-all: every GPU sends tokens TO and receives FROM every other Pattern changes every token — can't pre-schedule like CUDA graphs Hot expert problem: If everyone routes to Expert 7 → GPU 0 overwhelmed Other GPUs idle → load imbalance Fix: auxiliary load-balancing loss during training
🏙️ EMPIRE ANALOGY

256 specialist chefs, each expert in one dish (sushi, BBQ, pasta...), spread across 4 restaurant locations. Every customer order picks 8 specialists. The order must physically travel to each specialist's location. If Chef 7 (the famous pasta chef) is everyone's favorite, his location is overwhelmed while others sit empty — you need a maitre d' who forces variety to keep all locations busy.

Why EP tolerates cross-node better than TP: EP's all-to-all can overlap with local expert computation. TP's all-reduce is fully blocking — next layer can't start. EP is latency-tolerant by design, making cross-node EP viable where cross-node TP is not.

// 6. — CONTEXT / SEQUENCE PARALLELISM

Context Parallelism & Ring Attention 💍

🔄 Split the Sequence LONG CONTEXT
⚔️ Kills: KV cache overflow for ultra-long sequences

FlashAttention handles O(S²) compute within one GPU by tiling in SRAM. But for 128K+ token sequences, even O(S) KV storage overflows one GPU's HBM. Context Parallelism splits the sequence across GPUs.

128K token prompt, 4 GPUs: GPU 0: tokens 0–32K (Q_0, K_0, V_0) GPU 1: tokens 32K–64K (Q_1, K_1, V_1) GPU 2: tokens 64K–96K (Q_2, K_2, V_2) GPU 3: tokens 96K–128K (Q_3, K_3, V_3) Problem: attention is GLOBAL — Q_0 must attend to K_3, V_3! Ring Attention solution: Step 0: each GPU computes attention with LOCAL K,V Step 1: K,V rotate one step around the ring GPU 0 gets K_3,V_3 → accumulates partial scores GPU 1 gets K_0,V_0 → accumulates partial scores Step 2: rotate again, accumulate Step 3: rotate again, accumulate After T steps: every GPU has seen ALL K,V → full attention ✅ Online softmax (from FlashAttention) makes partial accumulation work Compute and ring communication overlap → comms hidden
🏙️ EMPIRE ANALOGY

A food critic must taste 10,000 dishes but her table only holds 2,500 at once. Four critics each hold 2,500 dishes and pass their trays around a circular table. Each critic tastes every combination in rotation, keeping running notes (online softmax) on the best flavors so far. After one full rotation: every critic has effectively tasted all 10,000 — but the table was never overloaded.

Primarily a prefill problem — 128K token prompt hits CP. During decode you generate one token at a time, but the accumulated KV cache still grows, so very long sessions eventually stress it too.

The Cost Table 📊

// THE LATENCY FLOOR — MULTI-NODE

InfiniBand round-trip: 2–5µs vs NVLink's ~100ns. TP cross-node: 160 blocking round trips × 2–5µs = 320–800µs added per token. PP cross-node: a few µs per stage boundary. This is why TP is forbidden cross-node and PP is the natural cross-node strategy.

// 8. — PRACTICAL DEPLOYMENT PATTERNS

How Real Systems Are Built 🏗️

// PATTERN 1

DP Across Nodes

Model fits on one node. Run independent replicas on each node. Zero cross-node communication during inference.

🏙️ ANALOGY

Franchise model. Each location is fully self-contained. No coordination needed. Just open more locations.

// PATTERN 2

TP within Node + PP across Nodes

Standard approach for large dense models. NVLink handles TP's frequent all-reduces. InfiniBand handles PP's rare activation handoffs.

🏙️ ANALOGY

Each building has its own tightly coordinated kitchen team (TP via dumbwaiter). Buildings connect via delivery truck (PP via InfiniBand) — trucks only carry one box between stages.

// PATTERN 3

TP within Node + EP across Nodes (MoE)

For MoE models. EP's all-to-all is more latency-tolerant than TP's all-reduce, making cross-node EP viable where cross-node TP is not.

🏙️ ANALOGY

Specialist chefs distributed across the city. Orders travel to wherever the right specialist works. The routing is flexible — unlike TP's rigid every-layer-sync.

// THE EXCEPTION

Cerebras WSE

One wafer = one chip = no boundaries. All of this becomes irrelevant. 44GB on-chip SRAM. No HBM. No inter-chip comms. The "delivery truck" problem simply doesn't exist.

🏙️ ANALOGY

One impossibly gigantic kitchen where every chef works side by side. No trucks needed. This guide's entire problem set dissolves.

// THE HIDDEN KV CACHE BONUS

More GPUs = weights spread thinner = more HBM per GPU free for KV cache. 70B FP16 on 8 GPUs: 17.5 GB weights per GPU, leaving ~62 GB for KV cache. With INT4 quantization: ~4.4 GB weights, ~75 GB for KV cache. TP isn't just about fitting the model — every additional GPU is also a throughput multiplier via larger serving memory.

The Complete Empire Guide 📖

// ONE UNIFYING IDEA

Every technique here fights the same battle: the wire between GPUs costs time. Design your parallelism strategy so that the most expensive communication travels the fastest wire, and the slowest wire carries the least data.

// HOW THE THREE SECTIONS FIT TOGETHER

Scheduling (Ch 5): Time is scarce — schedule requests to maximize GPU utilization.
Single Request (Ch 6): Memory bandwidth is scarce — minimize HBM trips within one GPU.
Hardware Scaling (Ch 7): Memory capacity + wire bandwidth are scarce — shard everything, match parallelism to interconnect speed.
